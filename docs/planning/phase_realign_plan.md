# Phase Realignment Plan — AI Wealth Office

Status: Draft after P3 completion.  
Purpose: realign future Px execution with the original stage roadmap in `docs/planning/implementation_plan.md` so the project stops drifting through mixed-stage execution.

## Why This Document Exists

P1 / P2 / P3 were effective for execution, but they did not stay perfectly aligned with the original stage buckets.

Reality today:

- some later-stage capabilities were partially pulled forward,
- some intended stage items are only partially complete,
- P4+ should no longer be improvised from local momentum alone.

This document resets the route from the **current actual system state** back onto the **original strategic stage map**.

## New Px Mapping From Here

## P4 — Trustworthy Research Operations
Primary stage targets:
- Stage 6 (finish)
- Stage 7 (finish)
- Stage 11 (operationalize)
- Stage 13 (formalize)

### Mission
Turn the current working office into a more trustworthy research office with repeatable decision packages, explicit safety/compliance review, and formal postmortem loops.

### Why this comes next
The system already runs.  
The next weakness is not “can it act?” but “can it act repeatedly with trustworthy outputs, repeatable close-out, and formal reflection?”

### P4 must deliver

1. **Decision-package maturity**
   - standard reviewed decision pack, not only memo + handoff
   - stable summary / evidence / risk / next-decision format

2. **Workflow asset discipline**
   - reusable asset registry beyond ad hoc documents
   - retrospective file and workflow registry become standard outputs

3. **Operational safety / compliance layer**
   - explicit research-only boundary package
   - formal risk and compliance checklist usage
   - clear rule for what cannot be automated

4. **Formal postmortem loop**
   - every accepted project produces a postmortem
   - worker reliability / failure patterns start getting recorded systematically

### P4 entry criteria
- P3 done
- PM-A operational
- closure automation exists
- backlog-first and numbering discipline already proven

### P4 exit criteria
- every completed issue can generate a reusable close-out package
- postmortem becomes standard
- safety/risk review is explicit rather than implied
- reusable workflow assets are intentionally catalogued

### Suggested first backlog themes
- decision package standardization
- safety/compliance checklist operationalization
- retrospective/postmortem template + registry
- worker scorecard seed

## P5 — Assetized Wealth Office
Primary stage targets:
- Stage 8
- Stage 9

### Mission
Move from a repeatable project office into a true wealth-office research system with asset libraries for data, strategies, conclusions, and reusable research context.

### Why after P4
Without trustworthy review and postmortem discipline, asset libraries will become messy archives instead of real assets.

### P5 must deliver

1. **Data asset library**
   - dataset catalog
   - metadata quality fields
   - validation status
   - known issues

2. **Strategy asset library**
   - strategy registry
   - migration status
   - dependency mapping
   - backtest / review history

3. **Research conclusion library**
   - what worked
   - when it worked
   - why it failed
   - next optimization direction

4. **Office-level orchestration**
   - a real multi-step wealth-office flow that touches assets rather than only one-off documents

### P5 entry criteria
- P4 decision-package trust layer in place
- postmortem and asset discipline started
- PM-A can keep backlog and project hygiene stable

### P5 exit criteria
- data and strategy assets are queryable and reusable
- the office can run a real research cycle using asset inventory, not only ad hoc files
- at least one project reuses prior assets cleanly

### Suggested first backlog themes
- dataset metadata schema
- strategy registry schema
- research conclusion schema
- first reusable asset-backed strategy/demo cycle

## P6 — Governed and Productized Office
Primary stage targets:
- Stage 10
- Stage 12

### Mission
Add governance, performance visibility, and product form so the office is no longer just an internal workflow, but an operable platform.

### Why after P5
Productization before assetization would create a shell without enough reusable substance.

### P6 must deliver

1. **Worker governance**
   - scorecards
   - success/failure rates
   - reviewer reliability indicators
   - routing recommendations backed by evidence

2. **Operating dashboard or equivalent workspace view**
   - project state
   - worker state
   - backlog truth
   - QC / rework visibility

3. **Product surface direction**
   - internal tool shape
   - workbench shape
   - copilot shape
   - SaaS/private deployment path

### P6 entry criteria
- asset library exists
- recurring project loop is stable
- governance can be based on real repeated runs, not one-off anecdotes

### P6 exit criteria
- worker routing uses governance evidence
- project state can be observed centrally
- product form is not speculative; at least one concrete internal workbench pattern exists

### Suggested first backlog themes
- PM-A / CEO scorecard workflow
- worker performance matrix
- project/issue dashboard spec
- internal workbench MVP plan

- Stage 14

Reuse the office operating system outside the quant/wealth domain.

### Why last

   - e.g. industry research office

   - content production office

2. Reusable core office skeleton

   - different data sources, prompts, QC, and report templates

### P7 entry criteria
- P6 done
- wealth-office core is stable enough to be exported

### P7 exit criteria
- at least one non-quant office runs on the same CEO / PM / worker / QC backbone

## Non-Negotiable Rules For P4+

### 1. Multica-first numbering
Real issue number first.  
Local file names follow the real issue number.

### 2. Real backlog before activation
No activation without a visible real backlog batch.

### 3. PM-A owns coordination hygiene
CEO should not be default operator for routine project hygiene.

### 4. Parallel when safe
If PM work and content work do not block each other, run them in parallel.

### 5. Closure checklist mandatory
Every issue phase change must pass closure review across:
- issue content
- planning
- project metadata
- execution system
- verification
